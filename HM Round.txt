## Terraform: it is IAC (infrastructure as code)

- terraform maintains a state file to track infra changes. (.tfstate)

# working of terraform internally ->
- There are 3 main stages: write, plan, apply
- providers: there are plugins to interact with cloud APIs like aws, gcp
- modules: reusable tf configurations
- state files: tracks infra state
- execution plan: tf plan shows proposed changes
- tf graph shows dependency resolution 

- Managing ec2 instances: terraform compares the current state (terraform.tfstate) with the desired state defined in the configuration file. If change is detected tf plan shows that modifications done. Then running tf apply updates the ec2 instance. 

- provider "aws" -> the provider interacts with the APIs of the cloud service.

- security groups acts as virtual firewall for EC2 instance. they control inbound and outbound traffic by defining rules. (ingress/engress)

- for dependencies of instance on security grp, first create sg and then pass on that in depend_on = [aws_security_group.example]

- aws_autoscaling_group is used to scale ec2 instance. we define the max, min, and desired no. of instances. If traffic spikes, it will scale automatically.
- It scales according to the policies defined based on cloudwatch alarms. (IT IS HORIZONTAL SCALING)

- to prevent merge conflicts, enable state locking with dynamoDb

- in dev env, use remote state backends like aws s3 with dynamodb for state locking.  
- for high availability, deploy across multiple availability zones. 

- create_before_destroy lifecycle rule to create new resource before creating old one. 

- to provision multiple ec2 instances with different configurations, use terraform's count or for_each meta-argument. 

- I once faced an issue where Terraform was unable to delete a resource due to a dependency conflict. After investigating, I realized the state file was out of sync with the actual infrastructure. I used ```terraform state rm``` to remove the resource from the state file and then re-imported it. I also implemented a remote backend with state locking to prevent such issues in the future.

for ec2 instance flow is like: 
- define providers
- define security group for alb and ec2 instance
- define ec2 instance and attach sg 
- Auto scaling grps: adjusts no. of ec2 instances in response to demand
- Auto load balancer distributes traffic across instances

### Kafka:
 
* I used kafka to decouple audio ingestion from processing.
 
- Kafka is distributed event streaming platform used for high level throughput, fault-tolerant messaging.

Kafka- distributed event streaming platform Meaning: 

- distributed: kafka is designed to run as a cluster of servers(brokers) that work together to store and process data. 
- data is partitioned across multiple brokers, allowing to scale horizontally. 
- event streaming: event is an individual piece of data like click, transaction. And stream refers to continuous flow of these data in real time. 
- Kafka is designed to handle real-time data streams, where events are produced, processed, and consumed as they occur.

* Kafka gives fan-out feature

- partition lies in server/broker level

- consumers pull the msgs from brokers so that consumers can work at their own pace (NOTE: WE dont push msgs to consumer, it pulls)


* RabbitMQ used for point to point messaging with lower throughput designed for reliable message delivery. This is because RabbitMQ uses acks. if any ack fails, we re-queue to deliver msg again

** Use RabbitMQ when u need point to point msg delivery with low throughput. 
** Kafka has guarantee of at least once delivery. Suppose for m1 is delivered, and offset is 1 rn. if m2 fails, offset does not get incremented, so we can pull m2 from the queue. On successful processing, consumer sends ack to increment the offset. 


RabbitMQ Reason for low throughput: architecture: Message oriented middleware
- treats each msg individually, creates overhead. 
- writes msgs in disk for reliability which is slow
- requires back and forth mechanism of acks 

** kafka is faster bcoz:
- log based architecture:
- provides batching, minimizes i/o operations
- can scale horizontally
- don't require acks, uses offset tracking
- offset is how many msg each consumer has received and when consumer needs data, kafka sends new data from that offset

* Kafka retains msg for longer period and allows multiple consumers to read the same msg.

#Components:
- Producer - publishes msg to kafka topics
- Topic: a channel where msgs are published
- Consumer: subscribe to topics and process the msg
- Broker: a server that stores data and serves client
- Partition: a topic is divided in to multiple partitions to enable parallel processing for scaling.
- Zookeeper: manages metadata and does the leader election process. manages and coordinates the kafka brokers. 

- Zookeeper:
- kafka keeps replica of each partition
- kafka has primary replica which do write ops and other does read ops
- every read replica pull msg from primary to stay in sync
- if primary write replica fails, zookeeper promotes a read replica to become primary. 
- *****how to maintain consistency? consumer will consume only those msgs which have been replicated across all replicas. 

- Ensuring fault tolerance and high availability : through replication. Each partition can be replicated across multiple brokers.

# Advantages of kafka over RabbitMQ:
- kafka has high throughput as it scales horizontally using partitions while the RabbitMQ scales vertically but struggles at high throughput
- kafka msgs are persisted on disk and retains them for a certain period of time while RabbitMQ deletes msgs once consumed.
- kafka maintains ordering whin a partition while RabbitMQ does not guarantee that. 
- kafka can easily scale horizontally, while RabbitMQ scales vertically
- in kafka msgs are stored in immutable logs, and consumer can replay old msgs (reset offset) while in RabbitMQ msgs are deleted after consumption unless ttl is set

* prefer RabbitMQ if your are using req-res architecture while kafka is preferred in when we need event streaming, real-time data pipelines.


## use case difference
- in kafka, the msg from the topic can be used by various services at same time like logging, transcription i.e single msg can be used in multiple places while in RabbitMQ one msg can go at one place.
This thing in kafka is known as FAN OUT.

- prefer RabbitMQ when we want msg routing. RabbitMQ has  architecture (producer - exchanges (msg routers) - queue(can be multiple) - consumer)
this exchange help to route msg efficiently 

##** Key Rule:
- All consumers within the same consumer group share messages (load balancing).
- Consumers in different consumer groups receive the full message stream (independent consumption).
* Kafka acts as a queue when multiple consumers belong to same consumer group


## MORE ON KAFKA

- kafka topic is split into partitions, each partition is ordered, durable and immutable 
- consumers within a group share partitions -- each partition is consumed by exactly one consumer
- if consumers > partitions, they sit idle

use case: 
- audio is published to a topic
# we have two services - transcription, logging
- then we will define two consumer groups 
- now each consumer group received a separate copy of the item


on the other hand if we had to implement same thing in RabbitMQ:
- RabbitMQ uses exchanges(message routers) and queues (message buffers) to control message distribution 
- this requires explicit exchange and queue setup (CON)
- since RabbitMQ does not have partitioning, instead there is a single queue, hence no parallel processing possible 
- RabbitMQ provides selecting routing which routes msgs based on routing_key 

** USE RABBITMQ WHEN U NEED SIMPLE TASK QUEUES OR FLEXIBLE ROUTING

## Persistence Mechanisms: this is optional, mainly done in-memory

- RDb(redis database file) : takes periodic snapshots of the dataset at specified intervals which is stored in binary file. Con is loss of data of current      snapshot if redis crashes while taking snapshot.

- AOF(append-only file) : appends all logs to file con: performance affected.

- Hybrid: (rdb+aof) : The RDB snapshot mechanism can be used for periodic backups, and the AOF log ensures that no write operations are lost, even if the server crashes between snapshots.

* Storage: Redis - in-memory Kafka: persistent (disk based)

- Redis cluster can be used to scale horizontally

- Redis sentinel: provides high availability by monitoring Redis nodes, alerting and automatically promotes replicate in case primary node fails.

### Websockets:

- websocket is a full duplex communication protocol that enables bi-directional communication bw a client and a server over a single tcp connection unlike http which follows req-res model

#working of ws
- handshake: client sends an http upgrade request to server -> if server supports ws, it responds with 101 switching protocols status code -> connection gets upgraded from http to ws then
- once connection is established, msgs are send via frames(text, binary, ping/pong, close)
- unlike http, no need to establish new connection for every msg

# How to scale ws? 
- distribute websocket connections across multiple backend servers, and use sticky session(session affinity) to ensure client connects to same server
- use pub/sub message broker to broadcast all messages to all connected servers, also ensures real time sync  bw instances
- use connection pooling to optimize server performance
- compressing the payload 


## how to handle connection drops? heartbeat mechanism, auto reconnect logic
- ping/pong heartbeats: send periodic pings framers from the server, if no pong received within a timeout, close the connection
- automatic reconnection: using exponential backoff 
- we can store client's userId, sessionId or token so that server can restore session state, and resubscribe to where it dropped


- Ws frames: are the smallest unit of data transmitted over a ws connection. Frame consists of a header (contains metadata like opcode, payload length) and payload (actual data)


# Alternatives of WS:
- SSE :  allows server to push updates to client over http but it is unidirectional
- long polling

# ws performance optimizations:
- compression: ws payload can be large, so use ```permessage-deflate``` ws extension to compress msgs. works best with text, json msgs
- batching msgs
- connection pooling: creating and destroying connection frequently increases latency and resource usage. 
- load balancing
